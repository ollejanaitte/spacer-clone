================================================================================
R0-07  Git / branch / PR / merge 運用方針
================================================================================
新システム開発の Git 運用を確定する。

--------------------------------------------------------------------------------
1. ブランチ構成
--------------------------------------------------------------------------------
- origin/main                 : 旧システム安定版（保全・変更しない）
- rebuild/integrated-system   : 新システム長期統合 branch
- feature/*                   : 小さい実装単位（新システム開発用）

--------------------------------------------------------------------------------
2. 基本フロー
--------------------------------------------------------------------------------
feature branch
→ 実装
→ test / typecheck / lint
→ PR（feature/* → rebuild/integrated-system）
→ review
→ merge（rebuild へ）
→ rebuild branch 再同期（pull）
→ 次の feature

--------------------------------------------------------------------------------
3. main への統合方針（重要）
--------------------------------------------------------------------------------
新システムが Acceptance Gate を満たすまでは、
未完成の新システムを毎回 main へ merge しない。

最終的な main 統合は後続 Phase で以下を通過してから行う:
- E2E
- Save / Load / Restart 検証
- Reference Business 001
- regression
- 数値検証

--------------------------------------------------------------------------------
4. ルール（AGENTS.md 踏襲 + rebuild 固有）
--------------------------------------------------------------------------------
- main へ直接 commit しない / origin/main へ直接 push しない。
- ワイルドカード add（git add . / -A）禁止。パス明示。
- force push 禁止。
- 既存 worktree・branch を削除・強制変更しない。
- dirty 作業を破棄しない。
- 作業は専用 worktree 内で行う。
- 各作業前に git fetch で最新を確認する。

--------------------------------------------------------------------------------
5. worktree 運用
--------------------------------------------------------------------------------
- 旧 main worktree : /home/masaharu/Projects/spacer-clone
- 新 rebuild worktree: /home/masaharu/Projects/spacer-clone-next
- feature 作業は /home/masaharu/Projects/spacer-clone-next 内で行う。
- 旧 worktree の dirty 変更は新 worktree に混入させない。

--------------------------------------------------------------------------------
6. PR 品質
--------------------------------------------------------------------------------
- typecheck / test / lint を必ず実施。
- 監査成果物・設計文書とアプリ実装は混在させない。
- PR には変更範囲と検証結果を記載する。
