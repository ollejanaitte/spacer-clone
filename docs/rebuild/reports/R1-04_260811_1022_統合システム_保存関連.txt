1. R1-04 目的
--------------------------------------------------------------------------------
R1-02で確定したProject Data CoreとR1-03で確立したProject Manager /
Project Repositoryを、実filesystem永続化・自動保存・再起動復元へ接続する。
「作成→自動保存→完全終了→再起動→業務一覧復元→開く→内容維持」の縦断を成立。

--------------------------------------------------------------------------------
2. 実装範囲
--------------------------------------------------------------------------------
Step A: filesystem persistence責任境界 + filesystem Repository
  - FileSystemGateway（memory/node/ipc）: storage非依存fs境界
  - ProjectPersistence interface / FilesystemProjectPersistence
  - FilesystemProjectRepository（async create/get/list/update/delete）
Step B: 自動保存 + 保存状態管理 + 保存失敗通知
  - PersistentProjectManager（mutation後自動persist・saving/saved/failed）
  - Electron IPC（projectPersistenceIpc / userData/projects）+ preload/main
  - IpcFileSystemGateway（renderer→main bridge）
  - SaveStatusIndicator（保存中.../保存済み/保存に失敗しました）
Step C: アプリ再起動復元 + 業務一覧再構築
  - restoreFromPersistence（valid project復元・invalid skip）
  - NextApp起動時restore + 読み込み中ゲート
Step D: 最小自動バックアップ
  - .backup/<timestamp>.spacerbak 自動生成・世代管理（保持5）・正本分離
Step E: filesystem縦断テスト + regression + Electron起動確認
Step F: Final Report（本ファイル）

--------------------------------------------------------------------------------
6. filesystem Repository構成
--------------------------------------------------------------------------------
- FileSystemGateway（memory/node/ipc）→ FilesystemProjectPersistence → 
  FilesystemProjectRepository（async）
- R1-03のInMemoryProjectRepository（sync）はUI runtime契約として維持
- ProjectManagerと責務分離・UIはfs直touchしない
- duplicate ID / not-found / invalid file を適切に処理

--------------------------------------------------------------------------------
7. Auto Save構成
--------------------------------------------------------------------------------
- UI mutation → PersistentProjectManagerがsyncでin-memory更新後、async queueで自動保存
- 保存状態: saving → saved / failed（listenerでUI通知）
- 連続編集はqueue直列化（過剰I/O・競合防止の最小設計）

--------------------------------------------------------------------------------
8. 保存状態UI / 保存失敗時の扱い
--------------------------------------------------------------------------------
- SaveStatusIndicator: 保存中... / 保存済み / 保存に失敗しました をヘッダー表示
- 保存失敗は黙殺せず、必ずUIで明示
- 失敗時もin-memory repositoryは破壊されない（次回mutationで再試行可能）

--------------------------------------------------------------------------------
9. 再起動復元結果
--------------------------------------------------------------------------------
- 作成→自動保存→完全終了→再起動→業務一覧復元→開く→内容維持 を実fsテストで確認
- 業務件番・業務名・設計段階（その他カスタム含む）・Project ID が維持
- 削除済みProjectは再起動後も復活しない
- 不正JSON / invalid schema file はskipされ正本に影響しない

--------------------------------------------------------------------------------
10. backup方式 / 頻度 / 保持数 / 保存場所
--------------------------------------------------------------------------------
- 方式: 自動保存成功時にシリアライズ済みProjectのJSONスナップショットを
  .backup/配下へ .spacerbak として生成（ZIP等の依存追加なし・最小基盤）
- 頻度: 自動保存（mutation）と連動
- 保持数: 5世代（超過分は自動prune）※R1-04で安全な最小値として採用
- 保存場所: <projectId>/.backup/
- backup失敗は正本保存を巻き込まない
