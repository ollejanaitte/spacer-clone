## Governed classes

| Golden type | Permitted oracle | Independence rule |
|---|---|---|
| `ANALYTICAL_GOLDEN` | Closed-form derivation, equilibrium, or independently derived invariant | Expected values must not be generated by the Apollo implementation under test |
| `REFERENCE_SOFTWARE_GOLDEN` | Checksum-fixed output of a fixed, licensed reference-software version | Native input/output, version, settings, units, conventions, and repeat runs are mandatory |
| `APPROVED_REGRESSION_GOLDEN` | Previously approved analytical/reference result or independently approved behavior artifact | Apollo output alone cannot originate or approve the baseline |

Permitted purposes are `ANALYSIS_GOLDEN`, `DESIGN_VERIFICATION_GOLDEN`,
`SERIALIZATION_GOLDEN`, `EXPORT_GOLDEN`, `PARITY_GOLDEN`, and `NEGATIVE_GOLDEN`.
Type and purpose are separate fields.

## Approval gates

A case is approved only after all of these gates pass:

1. model and expected artifacts are immutable and SHA-256 identified;
2. quantities, units, coordinate system, signs, and member-end convention are explicit;
3. derivation or producer identity is independent and reviewable;
4. absolute tolerance, relative tolerance, zero threshold, precision, and rounding rules are
   predeclared before observing Apollo mismatch;
5. a reference-software case records product/version/build, execution date, input/output checksums,
   and at least three isolated repeat runs;
6. a regression case traces to an already approved oracle and records the change-control decision;
7. negative cases assert a named rejection/status/diagnostic and cannot be reclassified as success;
8. the proposer and approver are distinct review passes, and approval is recorded in
   [golden_approval_register.csv](golden_approval_register.csv).

In the approval register, `independent_reviewer_and_approver` is the accountable approval identity
when `approval_status=APPROVED`; it must be a named person distinct from `proposer`. `review_date`
is then the approval timestamp, `decision_id` identifies the signed decision record, and
`evidence_reviewed` identifies the immutable manifest. Role labels are insufficient for an approved
row. Current rows use role labels only because every row is `NOT_APPROVED`.

## Reproducibility by class

- `ANALYTICAL_GOLDEN`: two independently prepared derivations must produce the same expected
  quantities and conventions; an Apollo run is not one of the two.
- `REFERENCE_SOFTWARE_GOLDEN`: at least three isolated runs of the fixed identity and input must
  satisfy the preapproved normalization and numeric policy.
- `APPROVED_REGRESSION_GOLDEN`: three isolated deterministic generations must match the immutable
  artifact after only approved variable-field normalization, and the parent oracle must already be
  approved.

`reproducibility_count` records only qualifying executions/derivations with retained manifests.
Ordinary CI repetitions and multiple assertions in one run do not increase the count.

Screenshots are supporting evidence only. Hand-edited expected output is prohibited. A tolerance
change after a mismatch creates a new proposal and requires independent justification and approval.

Missing, duplicate, malformed, or unmatched entities/quantities are failures, never skipped metrics.
An empty metric set cannot pass. Case identity participates in matching. A missing member-force
comparator means member-force coverage is blocked, not implicitly satisfied. Parser coercion of a
non-numeric token to zero is prohibited for Golden ingestion.

## Existing repository artifacts

Existing beam formulas and metadata are useful `REFERENCE_ONLY` candidates. Existing regression
tests and bridge-definition files prove current behavior, not independent expected truth. The
`examples/spacer-reference/` directory contains a format example but no qualifying licensed
reference corpus. None is silently promoted by DS-07; case-by-case blockers are in
[golden_case_catalog.csv](golden_case_catalog.csv).

The current Apollo numeric-authority guard continues to reject `GOLDEN_EXPECTED` registration.
DS-07 documentation completion does not lift that implementation guard; only the DS-09 numeric
release gate may authorize a later controlled change after all applicable evidence blockers close.

Portal-frame, simple-truss, and 3D L-frame metadata that proposes determining expected values after
the first implementation run is explicitly rejected as an oracle-generation method. The inline
values in `frontend/src/verification/spacerReference.test.ts` are parser/comparator test data, not
SPACER machine evidence.

## Change control

An approved Golden is immutable. Replacement requires a new artifact checksum, reason, source,
reviewer, approval record, and supersession link. Failing implementation changes do not authorize
editing the expected artifact. Suspected oracle defects move the case to fail-closed blocked status
until independently resolved.
