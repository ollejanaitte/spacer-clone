================================================================================
Phase 0 / STEP 1-11  コード品質・構造的問題監査
監査日: 2026-08-10
状態: CONFIRMED（コード実測 + サブエージェント調査）
--------------------------------------------------------------------------------
ユーザーに見える症状と、構造的な原因候補を分けて記録する。
================================================================================

--------------------------------------------------------------------------------
1. 巨大コンポーネント
--------------------------------------------------------------------------------
- App.tsx: 1752行。全ルーティング・状態管理・全ツールのバインディングを一手に保持。
  - 症状: 変更の影響範囲が広い、テストが複雑、依存が密結合。
- ApolloPhase1Shell.tsx: 2716行。
- 状態管理（useState 多数）と UI と API 呼び出しが同一ファイルに集積。
- 原因: ルート単位のコンポーネント分割が進んでいるが、ワークスペース本体の
  関心分離が不足。

--------------------------------------------------------------------------------
2. UI と計算ロジック・persistence の混在
--------------------------------------------------------------------------------
- App.tsx 内に、saveProject / 各種解析 / export / hydration が同居。
- viewer/ は描画と状態管理が Viewport 内に集積。
- persistence がコンポーネント直書き（localStorage 直接アクセスが各所に散在）。

--------------------------------------------------------------------------------
3. 保存処理の分散
--------------------------------------------------------------------------------
- 保存先が「download / native file / localStorage / backend/data / IF3サイドカー」
  に分散し、正規保存経路が一意でない。
- /api/projects/save（backend 実装済み）が UI 未使用 = 二重実装。
- autosave は AUTOSAVE_ENABLED=false で凍結、残骸コード。

--------------------------------------------------------------------------------
4. duplicated state（多重管理）
--------------------------------------------------------------------------------
- result / if3Result / rightResult / analysisResults.timeHistory（4重）
- project.nodes/members（FEM）と apolloPhase1Unit2（別コピー）
- project.supports（FEM 支点）と下部工 Support[]（配置）
- 座標系の暗黙定義5箇所（coordinateTransform/alignmentAdapter/substructure/apollo/cbdm）
- LINER domainDraft と roadDesignDocument（永続化変換）

--------------------------------------------------------------------------------
5. sample データの本番混入
--------------------------------------------------------------------------------
- mountain-viaduct-500 サンプルが /pro の「サンプルを読み込む」から読み込まれる
  （FEM サンプル期待の UX 不一致）。
- /api/examples の FEM サンプルが UI 未配線（loadExamples 未使用）。
- サンプル業務（checksum 偽値）が BusinessProject の標準として利用可能。

--------------------------------------------------------------------------------
6. hard-code / magic number
--------------------------------------------------------------------------------
- grillage STEEL_MATERIAL / declared_section（backend/engine/grillage.py:19-48）
- bridge_fem_generator 材料/断面定数（:376-395）
- DEFAULT_APOLLO_BRIDGE_GEOMETRY_DEFAULTS（apollo/visualization/types.ts:232-265）
- mountain sample の下部工寸法（substructure.ts:42-46）
- App.tsx:151 AUTOSAVE_ENABLED=false
- sampleBusiness checksum "0".repeat(64)

--------------------------------------------------------------------------------
7. mock / placeholder の残存
--------------------------------------------------------------------------------
- level0/ 16ファイルが「// T## で実装予定」
- 下部工 designEngine 15チェック hold_not_available / test-mock エンジン
- learn_links.json 全件 example.com/placeholder
- BridgeWizard の材料/断面 placeholder

--------------------------------------------------------------------------------
8. legacy route / dead code
--------------------------------------------------------------------------------
- backend/rule_engine/ 全体（約50モジュール）が app/engine から import 0件 = DEAD
- if3_legacy_compatibility.py（テストのみ）
- integratedScene3d.ts（テストのみ）
- /api/if3/availability（フロント未使用）
- /th/* → /pro/th/* リダイレクト（レガシー）

--------------------------------------------------------------------------------
9. frontend/backend contract 不明
--------------------------------------------------------------------------------
- /api/design/analyze の docstring は NOT_AUTHORIZED、実コードは NOT_GRANTED（不一致）
- 移動荷重 result のスキーマが resultViewModel の想定と不一致（クラッシュ原因）
- rule_engine の契約（backend）と LINER（frontend）のパラレル実装が統合されていない

--------------------------------------------------------------------------------
10. Electron/Web 責任境界
--------------------------------------------------------------------------------
- preload/spacerDesktop ブリッジはファイルダイアログのみ。
- バックエンド起動は start-ubuntu.sh（外部）または packaged 時の spawn。
- renderer は常に http://127.0.0.1:5173 前提（dev）。パッケージ時は loadFile。

--------------------------------------------------------------------------------
11. test 不足
--------------------------------------------------------------------------------
- フロント: Vitest（単体・サブシステム）+ Playwright E2E（多数）。
  - ただし移動荷重クラッシュを検出する E2E/単体が無い（回帰網の穴）。
- バックエンド: pytest 86ファイル（エンジンは良くテストされている）。
  - rule_engine はテストのみが消費（本番配線なし）。
- 保存/再起動（Persistence）E2E: 不十分。STEP 1-06 のデータ損失リスクを
  検出する自動テストがない。

--------------------------------------------------------------------------------
12. schema / migration
--------------------------------------------------------------------------------
- schemas/project.schema.json（67KB）は存在。
- projectMigration.ts は実質 schemaVersion 付与のみ。
- LINER/Apollo のマイグレーションは hydration 関数が個別に担う（分散）。
- CBDM/manifest の保存スキーマに対する実体が未実装。

--------------------------------------------------------------------------------
13. project lifecycle 不在
--------------------------------------------------------------------------------
- Open→Edit→Save→Close→Reopen のライフサイクルが明示的に管理されていない。
- 未保存の警告は Apollo のみ。
- autosave/recovery が凍結。

--------------------------------------------------------------------------------
14. 型不整合・optional 濫用
--------------------------------------------------------------------------------
- movingLoadResult のレスポンス型と ResultViewModel の入力型の不整合（クラッシュ根因）。
- optional 値（result.displacements 等）の前提検証不足。

--------------------------------------------------------------------------------
15. geometry 生成責任不明
--------------------------------------------------------------------------------
- 3D 生成が「Viewer3D（FEM）/ Main3D（サンプル）/ Apollo（既定断面）/
  下部工（Support）」に分散。共通のジオメトリソースが無い。
- CIM 実装なし。

--------------------------------------------------------------------------------
16. 結論
--------------------------------------------------------------------------------
- 中核の解析エンジンと LINER 線形計算は実装・テストが充実。
- しかし「UI 集約（App.tsx）」「保存分散」「多重状態」「DEADコード多数」
  「フロント/バック契約不一致」「テストの穴（移動荷重/永続化）」が
  統合システム化を阻害する構造課題。
- 特に: 移動荷重クラッシュは「契約不一致 + 型前提不足 + テスト網の穴」の典型。
