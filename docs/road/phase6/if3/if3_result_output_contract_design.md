# IF3 Result / Output Contract Design

**Date:** 2026-07-25
**Status:** DESIGN_DEFINED_REVIEW_READY
**Contract name:** `FrameAnalysisResultResource`

## Baseline Verdict

Before this design package, the IF3 contract verdict was `NOGO`. Evidence shows that the conceptual
Persisted Result Resource exists in planning docs, and `BridgeFrameAnalysisDocument` has optional
`persistedResultRefs`, but the concrete implementation is missing.

Current implementation gaps to preserve:

- Stable result identity is absent.
- Model/result binding is absent or implicit through `projectId` only.
- Document `Provenance` exists, but `AnalysisResult` lacks result provenance.
- Analysis-result staleness is missing.
- Persisted result resource is not implemented; `persistedResultRefs` exists but is not populated as
  an authoritative index.
- Report and Viewer code paths consume raw `AnalysisResult` in places.
- DRAFT result contract is missing.
- Backend/frontend responsibility boundary is incomplete.
- Schema and migration policy for IF3 is not implemented.

## Single Source of Truth

The authoritative result flow is:

```text
BridgeFrameAnalysisDocument
  -> Analysis Request
  -> Solver Raw Result
  -> Normalized IF3 Result Resource
  -> Report / Viewer / DRAFT adapters
```

`BridgeFrameAnalysisDocument` is the source model contract. The solver raw result is transient
implementation output. `FrameAnalysisResultResource` is the first authoritative result artifact.
Report, Viewer, and DRAFT adapters consume only validated result resources or DTOs derived from
validated result resources.

Direct authoritative consumption of raw solver `AnalysisResult` by Report, Viewer, or DRAFT is
prohibited. A raw `AnalysisResult` may be accepted only as compatibility input to a normalizer that
emits diagnostics and either produces a valid result resource or fails closed.

## Resource Envelope

`FrameAnalysisResultResource` is an immutable persisted-result resource with this required envelope:

| Field | Required | Rule |
| --- | --- | --- |
| `schemaId` | Yes | Exact result contract family, recommended value `frame-analysis-result-resource` |
| `schemaVersion` | Yes | Supported SemVer only; unknown major fails closed |
| `resultId` | Yes | Stable UUID generated once per normalized result resource |
| `analysisRunId` | Yes | Stable UUID for the solver run attempt that produced or failed to produce this resource |
| `sourceDocumentId` | Yes | Bound `BridgeFrameAnalysisDocument.documentId` |
| `sourceDocumentVersion` | Yes | Bound frame revision identity, using `revisionId` unless implementation introduces explicit immutable revision refs |
| `sourceContentChecksum` | Yes | Exact `BridgeFrameAnalysisDocument.contentChecksum` used for the run |
| `status` | Yes | One of the IF3 statuses below |
| `generatedAt` | Yes | ISO-8601 UTC timestamp generated by the backend normalizer |
| `solverName` | Yes | Solver/tool family, for example `scipy_sparse` or `newmark_beta` |
| `solverVersion` | Yes | Backend/app/algorithm version sufficient for compatibility checks |
| `analysisSettingsChecksum` | Yes | Canonical checksum of settings and analysis definition used for the run |
| `loadContext` | Yes | Load cases, combinations, influence/moving-load/time-history request IDs and checksums |
| `provenance` | Yes | Result provenance, separate from document provenance |
| `diagnostics` | Yes | Ordered validation/solver/result diagnostics |
| `payload` | Yes for non-empty result states | Typed result payload catalog |

Optional fields:

| Field | Rule |
| --- | --- |
| `transferPackageId` / `transferRecordId` | Present when frame model was created or updated from Road-to-Frame transfer evidence |
| `modelRevision` | Explicit immutable model revision identifier if added separately from numeric `revisionId` |
| `resultChecksum` | Canonical checksum of the normalized result resource excluding mutable transport metadata |
| `unitSystem` | Exact result unit/sign convention context when not fully inherited from source document |
| `capabilities` | Supported/partial/absent flags for result families |
| `resultKinds` | Declared keys present in `payload` |
| `createdBy` | Actor shorthand when not otherwise sufficient in `provenance.createdBy` |

## Statuses

| Status | Meaning | Authoritative export |
| --- | --- | --- |
| `PENDING` | Request accepted but no run has started | Block |
| `RUNNING` | Run is active or queued in active execution | Block |
| `SUCCEEDED` | Payload is complete, valid, current, supported | Allow |
| `FAILED` | Solver or validation failure, no authoritative payload | Block |
| `PARTIAL` | Some supported payload exists with known omissions | Conditional; only explicitly supported diagnostic output allowed |
| `INVALID` | Resource shape, numeric data, or binding failed validation | Block |
| `STALE` | Bound source/checksum/settings/load no longer matches current source | Block authoritative output |
| `UNSUPPORTED` | Schema/result kind/version cannot be consumed by this build | Block |

Result resources do not mutate. A rerun creates a new `analysisRunId`, `resultId`, resource, and
checksum. Marking a result stale is a derived consumer state or a new registry/reference state; it
must not rewrite the immutable historical resource payload.

## Payload Model

The payload is a result-kind keyed catalog:

```text
payload:
  linearStatic?
  eigen?
  responseSpectrum?
  influenceLine?
  movingLoad?
  timeHistory?
```

Each result kind owns typed rows with stable frame entity IDs, load context IDs, quantity names,
units/sign conventions, and numeric validation. Viewer indices, display labels, selected tabs,
camera state, and print layout state are forbidden in payload.

The implementation may expose a typed union at API boundaries, but the persisted resource must be
able to hold multiple result kinds for analyses that legitimately compose outputs, for example
moving-load results that include an influence result snapshot. `resultKinds` declares which payload
keys are present. Unsupported payload keys fail closed unless explicitly optional and preserved in a
namespaced extension area.

## Identity Generation

Backend owns `analysisRunId` and `resultId` generation because it owns solver execution and result
normalization. Frontend may generate client request IDs for correlation, but client request IDs are
not result identity.

Rules:

- `analysisRunId` is created when an analysis request is accepted.
- `resultId` is created when the normalizer creates the immutable resource envelope.
- `resultId` must be globally unique within the result-resource namespace.
- Duplicate `resultId` blocks registration and authoritative consumption.
- `resultChecksum` is computed after normalization using canonical ordering and numeric
  representation.

## Binding Design

Result-to-source binding is explicit:

- `sourceDocumentId` matches `BridgeFrameAnalysisDocument.documentId`.
- `sourceDocumentVersion` matches the exact frame revision used for the run.
- `sourceContentChecksum` matches the exact frame source content checksum.
- `analysisSettingsChecksum` matches the exact solver/settings block used for the run.
- `loadContext` references load cases, load combinations, influence lines, moving-load cases,
  time-history request data, and their checksums where applicable.
- `solverName` and `solverVersion` identify the producing solver family and compatible algorithm.

Consumer-to-result binding is also explicit:

- A Report, Viewer, or DRAFT request must name a `resultId` or use a validated current-result pointer.
- Implicit "latest result" selection is disallowed.
- A current-result pointer is allowed only if it is itself persisted/registered, bound to an exact
  source document ID/version/checksum, and validated before use.
- Ambiguous selection between multiple valid results blocks authoritative output.

## Provenance Design

`FrameAnalysisResultResource.provenance` is required and distinct from document provenance. It must
include:

- `createdAt`
- `createdBy`
- `producer.toolId`
- `producer.toolVersion`
- optional `producer.algorithmVersion`
- optional run environment metadata where needed for reproducibility
- source request/checksum references sufficient to audit normalization

Ownership:

| Field group | Owner |
| --- | --- |
| Run timing and solver producer | Backend |
| Source document identity/checksum | Shared contract validator, supplied by request builder |
| Actor/request correlation | Frontend initiates, backend records |
| Result normalization provenance | Backend |
| Report/export/viewer usage provenance | Consuming adapter records separately; it does not rewrite result provenance |

Missing provenance produces `MISSING_PROVENANCE` and blocks authoritative output.

## Persistence Policy

IF3 uses the Hybrid policy:

- Persist result metadata and immutable resource references.
- Persist validated payload when authoritative reload/export/viewer behavior requires it.
- Store authoritative references from `BridgeFrameAnalysisDocument.persistedResultRefs`.
- Treat old `AnalysisResult` as compatibility input only; it is non-authoritative unless wrapped,
  validated, checksummed, and registered as `FrameAnalysisResultResource`.

Reload behavior:

- Load the frame document.
- Resolve `persistedResultRefs`.
- Validate each referenced result resource schema/version/checksum/binding.
- Derive current, stale, failed, partial, invalid, and unsupported availability states.
- Never silently promote an old raw result to current authoritative output.

## Versioning And Migration

`IF3_SCHEMA_CHANGE_REQUIRED: YES`

Implementation requires a new result resource schema. A `BridgeFrameAnalysisDocument` schema change
is likely required to make `persistedResultRefs` authoritative rather than optional evidence.

`OLD_ANALYSIS_RESULT_POLICY: READ_OLD_WRITE_TARGET`

Rules:

- Old `AnalysisResult` is readable only as compatibility input.
- Unknown result-resource major versions fail closed.
- Minor compatible versions may be read only if unknown optional fields are preserved or ignored by
  explicit rule.
- Migration never invents missing stable result identity, binding, checksum, provenance, or payload.
- Legacy transient results with insufficient identity remain non-authoritative.

## Fail-Closed Conditions

The following block authoritative output:

- Missing identity
- Source binding mismatch
- Version mismatch
- Stale result
- Missing provenance
- Unsupported schema
- Invalid or partial payload outside an explicitly allowed diagnostic surface
- Ambiguous result selection
- Duplicate result ID
